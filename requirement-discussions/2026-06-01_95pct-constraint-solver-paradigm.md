# 95% 筹码动作捕获 — 约束求解器范式 + 离线原型判决

> **2026-06-01 战略转向后的核心设计串。** 底线从「50-70% directional」重设为
> **「筹码动作捕获率 95%」**(用户明示愿付架构级代价,见 memory [[data-reliability-50-70-percent]] §0)。
> 本 doc 沉淀:架构探索(3 个方案)→ 约束求解器综合 → **离线原型实测判决**。
> 关联:[[主题-数据质量]] · [[ring-beam-inference-design]] · phase-1-5 注意力方案(已封存 `_archived/2026-05-30_*`,其高帧思路被本范式收编)

## §0. 一句话结论(先读这条)

**范式 = 有条件可行。** 风险**干净地从「求解器聪不聪明」挪到了「捕获质量」**:

> 范式能成,**当且仅当**过三关:
> **① 底池总额读到高可靠(锚点,现 ~92%)**
> **② 事件流(谁/何动作类型/顺序)抓得够全(用来把池子分摊到各家)**
> **③ "永不渲染"地板 <5%(预设/瞬间动作至少有可读帧,否则物理封顶,见 §8 #2)**
>
> ①② **正是高帧 + CNN 要解决的**;③ 须先实测(§8)。目标因此收窄:**不用读准所有金额,只要把「底池」+「事件流」抓好**,金额由规则解出来。
> ⚠️ 求解器的完整输入不止"动作",还要盲注/起始 stack/位置 —— 见 §3.1。

## §1. 战略转向(2026-06-01)

- 旧底线「50-70% directional、别追 80%」**退役**(memory §0/§6 已改写)。
- 新底线 = **筹码动作捕获率 95%**(每个人的 下注/跟/加/弃 95% 都逮到)。现基线 ~75-80%,pot-gap silent ~25% → 目标 ~5%。
- **不是**单手完整复盘 95%(更狠,本次没选);风格分类已 75-85%,不是瓶颈。
- **为何 95% 在 image-only 红线下非物理不可能**:三轮深挖(fold/pot-gap/stack)证实漏因是 **per-tick OCR 读空 + 多 actor 同帧**,信息**确实在屏上停留过 ~1s**,不是信息不在屏上。→ 攻法:**高帧(4-10Hz)+ 多帧时序融合 + 状态机**。

## §2. 架构探索(3 方案,逐一压测)

### 方案 1:变化门控(capture-all → diff → 只 OCR 变化区)— **降级为二级优化**
- 思路:10Hz 抓全屏 → 帧差找"哪块变了" → 只把变化区交 OCR。抓屏/帧差极廉,OCR 是唯一瓶颈,门控把"全量 OCR"降成"只读变化"。
- **致命弱点(adversarial 挖出)**:
  1. **省在闲时,扎堆在硬时**:漏失发生在 preflop 多人连环动作的爆发期,那时一堆区同时变 → OCR 需求尖峰 → 照样排不上队。**瓶颈没消失,搬到了最硬的时刻。**
  2. **最想抓的信号比噪声还小**:小注(200→196,几个像素)的帧差 < timer 跳秒/筹码飞动的帧差 → 调高门槛滤噪声会**连小额真动作一起滤掉**。
  3. 坐标必须像素级稳定(比 OCR 更脆)、动作期 overlay 连续变化、表情/贴纸假扳机、高帧撞撕裂帧。
- **判决**:**不当主路径。** 真到吞吐顶不住,再当二级优化加回来。

### 方案 2:高频全量 OCR(不门控,每帧全读)— **更优,但需便宜化**
- 躲过方案 1 弱点 1+2:不门控 = 需求恒定可备足(治爆发期)、无帧差门槛(治小额淹没)。逻辑简单一个量级。
- **前提**:每帧 OCR 必须变便宜(原版 EasyOCR 重型,提不到 10Hz)。→ 引出方案 3。

### 方案 3:三档专项识别器(用户构想:除 ID 外不用重型 OCR)— **便宜化的具体打法**
把字段按识别难度分三档(纠正用户的"两分法",中间藏了数字这档):

| 档 | 字段 | 打法 | 难度 |
|---|---|---|---|
| **A 类别** | 动作词(弃/跟/加/让/下)、牌型、按钮、fold | **CNN 分类**(同识牌,val 100% 先例) | 中 + **持续手工标注** |
| **B 数字** ⚠️ | stack/下注额/底池/赢额 | **轻量数字识别器**(切位/固定槽,非分类器、非重型 OCR) | **中-高,最弱、错最狠、最没先例** |
| **C 开放文本** | 玩家 ID | 留重型 OCR,**低频缓存**(每座只首见/换人读一次) | 低 |

- **关键洞察**:目标(95% 筹码动作=金额)恰住在**最弱的 B 档**;A 档是 slam dunk 但**不是目标所在**。
- B 档错的后果重(切错一位=十倍误差),筹码守恒抓粗错抓不住细错(200 vs 209)。

## §3. 约束求解器综合(用户直觉 + 反思 + 德州规则三合一)

**核心反转:别再"读数字",改成"解数字"。**

德州规则下,**绝大多数金额不是任意数,是被规则定死的**:
- 跟注 = 当前注额(已知,不用读)
- 盲注 = 固定;最小加注 = 算得出;stack 单调减
- **真正"自由、必须读"的只剩「主动下注/加注额」一种** → B 档读数字负担大半被砍掉。

规则同时干三件 CNN/像素干不了的事:
1. **看穿遮挡**:all-in 时 stack 被胜率%盖住,但若廉价抓到"他动了"(A 档),金额由"跟注=已知/守恒/合法区间"**反解**。
2. **当垃圾过滤器**:违反"合法动作/单调 stack/守恒"的高帧中间态读数 → 直接判废(CNN 缺的"我不知道"机制)。
3. **解多人同帧**:timer 唯一性 invariant + 顺时针 → 即使两读数挤一帧,顺序定死。

**最深一层**:一手牌被规则**高度超定**(~20 事件,可靠抓 ~15 + 守恒 + 规则 → 解出剩 5)。
→ **完整度来自"解超定方程",不来自"读得准"** → 可在单帧读准率 <95% 下做到 95% 捕获。

**与圈梁关系**:圈梁是种子(手末兜底);本范式把它**从兜底提拔成脊梁**,由高帧事件流喂养,规则做实时求解+过滤+定序。

### §3.1 求解器输入清单(2026-06-01 复检补 — "解数字"不止靠动作流)

PokerKit/求解器要跑,需**一整套输入**,不只动作流。各输入的获取可靠性:

| 输入 | 用途 | 获取现状 / 可靠性 |
|---|---|---|
| **动作流**(谁/类型/顺序) | 主驱动 | 高帧+融合主攻;现残(§4.1) |
| **盲注级别 SB/BB(stakes)** | PokerKit post 盲注 + 算跟注/最小加注的基准 | 🔴 **§4 实测 `stakes="0.00/0.00"` —— 当前根本没抓!** 必须补:读 stakes 显示(固定 UI,应易)或从最小强制投入反推。**"规则定死跟注/盲注"全压在这个输入上,不补则链条断。** |
| **起始 stack** | 检测 all-in + 边池 + stack 单调约束 | 🟠 §4 实测不可靠(只看到 22-50% 池);高帧+融合待提 |
| **按钮/位置** | 行动顺序 + 盲注位 | 🟡 庄家钮捕获可靠性未验(YOLO 检测或现有 button_indicator ROI) |
| **底池总额** | 守恒锚点 | 🟢 ~92%(§4 发现2) |

→ **复检发现的真断点**:盲注级别没抓(stakes=0.00)。**T126 测量地基 / T125 应顺带确认 stakes 与按钮的获取**,否则求解器缺基准输入。
→ **Hero(自己座位)是 trivial 例**:不 silent、底牌已知、动作自见 → 重点是对手 villain 的重建。

## §4. 离线原型判决(2026-06-01 实测,DB 1455 手)⭐

> **目的**:在砸几个月前,用零成本离线数据回答"范式可行吗"。
> **诚实前提**:DB 数据本身是 OCR 那 ~75-80% 产物,**非 ground truth**;能做的是
> 内部一致性 + masking,**不能**验"还原真实牌局"。

### 发现 1:stack **不能**当锚点
- `v_hand_conservation`:仅 **21%(325)** 手 Σ(init-final)≈rake 通过;**75%(1130)CHECK_REQUIRED**。
- `v_ring_beam_rake_observed` 拆解:rebuy_likely(final≫init)**59%** / rake_high 14% / normal_rake 仅 **9%** / tiny 12%。
- **根因不是 OCR 读垃圾值**(逐玩家值都正常),而是:
  - **(a) 赢家投入天然隐藏在净额里**(init-final 对赢家 = 投入 − 赢得 = 负数,看不出投了多少)
  - **(b) 每人漏抓一点中下注,8 人一叠 Σ 漂几百**
- **样本 cd6883ba(pot=1206)**:输家捕获投入合计仅 **260**,赢家净 +484(实投 ~722 全隐形),~224(18%)非赢家下注漏抓 → **stack 只"看见" 260/1206 = 22% 的池**。

### 发现 2:底池 **能**当锚点(~92%)
物理不可能检查(底池必须 ≥ 输家投入 + ≥ 赢家净得):
- 底池 ≥ 输家投入:**1383/1455 = 95%** 通过
- 底池 ≥ 赢家净得:**92%** 通过(7.6% 硬违反)
- **中位数 赢家净得/底池 = 0.45**(p25 0.25 / p75 0.62)→ 物理合理,典型手底池没读飞
- 中位 输家投入/底池 = 0.32
- ⚠️ 那个吓人的 **均值 1.79 是 rebuy_likely 垃圾手离群点拉爆**(已看中位数证伪,**没被均值二次骗到**)
- **必要非充分**:只能查"底池读太小",查不出"底池读太大"(无 ground truth);~8% 硬不一致。

### 发现 3:求解器逻辑**不是**风险;完整可解性**离线验不了**
- 求解器非瓶颈(规则现成、圈梁 view 已建大量原语)。
- 但"pot + 事件流 + 规则 → 分摊各家"**依赖完整事件流**,而事件流就是那个残的 75-80% 捕获 → **要验整套,必须先有高帧的更干净数据**。

### 自我纠正(数据驱动 mandate)
- 上轮宣称"层4求解器离线**全验**、最高信息最低成本"——**"便宜"对了,"全验"错了**。离线能证的(锚点可用性、求解器非瓶颈)已证完,**剩下必须靠真捕获**。fail-fast 价值兑现:几条 query 就把风险从"求解器"重定位到"捕获质量"。

### §4.1 PokerKit replay 实测(2026-06-01,动作级确认)
装 PokerKit 0.7.4 验通 API 后,尝试拿录下的动作序列做 masking → **做不下去**:
- 全库 **post_sb/post_bb 仅 ~437 次 / ~1455 手 = 30% 的手才捕获盲注**;70% 连盲注都没有。
- 样本手 002f7b72(pot=70):preflop pot_after 一上来 46,但只捕获 8 筹码的动作 → **大半 preflop 缺失**;还有重复 bet(seq6 无金额 + seq7 bet24)、pot_after 不随动作更新。
- → **动作流缺 ~60-70% 且自相矛盾,凑不齐 PokerKit 要求的合法序列** → masking 无从谈起。
- **结论(动作级,比守恒聚合更细)**:离线数据**无法**验证求解器,瓶颈无歧义 = 捕获完整度。
- **银边**:PokerKit 引擎已就绪;高帧拿到干净数据后即可验。**T125 新增严指标:高帧后「有多少手能形成 PokerKit 可合法 replay 的序列」**(比 pot-gap 更硬)。

## §7. 外部信息核查(2026-06-01 — context7 + web search + 读码,全实证非印象)

走 [[dev-rule-validate-blind-spots]] MCP 信息饥饿红线,核查了影响方案成败的盲区:

### §7.1 三个最吓人的假设被现成工具拆掉

| 库 | 发现 | 对方案的影响 |
|---|---|---|
| **EasyOCR** | `Reader.recognize(img_grey, horizontal_list=[bbox], allowlist=...)` **原生支持只识别不检测**;`readtext_batched()` 批量 | **便宜化不必先训 CNN** —— 可用 recognize-only 免训练起步,把手工标注负担推迟到确认需要时 |
| **PokerKit**(High rep,uoftcprg) | 完整 NLHE:动作 API + **自动边池**(`state.pot_amounts`)+ **合法性 oracle**(`can_complete_bet_or_raise_to(x)` 查 min/max 区间)+ `check_or_call` 返回跟注额 + `state.stacks` + **可自定义 rake 函数**(`rake(amount, percentage, cap, no_flop_no_drop)`) | **求解器脊梁现成**:从"自建德州规则+边池+rake 数学"降到"接事件流 + 反向搜索"。**连 LR4 rake 漏点都堵上**。诚实边界:PokerKit 是**前向模拟器**,反向填补搜索仍是我们的,但用它当前向模型试探+校验 |
| **DXcam**(2026 维护) | Desktop Duplication,默认 60fps / 可 120;区域抓取 + 零拷贝 + 线程 ring buffer(`get_latest_frame`) | 我们要的 4-10Hz **远低于天花板,捕获非瓶颈**;线程 buffer 模型 = 天然"抓屏与处理解耦" |

### §7.6 OCR 模型谱系(2026-06-01 context7,轻↔重选型)

EasyOCR 是中量;两端都有现成更优:

| 模型 | 大小 | 准确率* | 定位 |
|---|---:|---:|---|
| 自训微型数字 CNN(造) | 极小 | 单字体可极高 | 最轻,同识牌打法 |
| **PP-OCRv4_mobile_rec** | **10.5MB** | 78.7%(通用) | **轻端**:英文+数字专用、recognition-only、TensorRT |
| EasyOCR(现状) | 数十 MB | — | 中量 |
| **PP-OCRv4_server_rec_doc** | **182MB** | **86.6%** | **重端**:15000+ 字含繁体 → 玩家 ID 最准 |
| Dots MOCR(3B VLM) | GB 级 | SOTA | **出局**:vLLM/秒级,杀牛用核弹,最多离线兜底 |

\* 通用 benchmark,**非单字体**;单字体数字微调后远高于 78%。
- **落点**:B 档数字 = 自训 CNN(最轻)或 PP-OCRv4_mobile_rec(现成,可微调单字体);C 档 ID = PP-OCRv4_server_rec_doc。
- **可用"更准"端是 CNN 识别器(PP server),不是 VLM**(VLM 太慢,不进高帧循环)。
- **PaddleOCR = #LR2 落地**,横跨轻/重。**坑**:PaddlePaddle 框架(Blackwell 支持存疑)→ 用 **PaddleOCR2Pytorch** 转 PyTorch 跑,留在我们栈。
- **T125 加 bake-off**:`EasyOCR recognize-only` vs `PP-OCRv4_mobile_rec` vs `自训数字 CNN`,比速度+单字体准确率。

### §7.7 YOLO 检测前端(2026-06-01 context7)— #LR1/#LR3 最佳实现

YOLO11n/12n:**5070 Ti 上 ~1ms/帧**(T4 TensorRT 1.64ms),~3-6MB,**PyTorch**,自定义类训练极简 → 10Hz 下成本可忽略。三接口:
- 🟢 **A 鲁棒元素检测前端(最大价值)**:一次 pass 找出所有元素(牌/筹码/下注区/timer/钮/overlay)位置 → 替掉固定 ROI。**治坐标脆弱(高帧会放大)+ 8v9 桌型割裂(一套搞定,免两 profile)+ UI 改版脆弱**。流程:YOLO 找 → 检测到的小图喂识别器读。**比 §主题-数据质量 讨论的 VLM grounding 强得多**(目标检测的本职就是找坐标,YOLO 主场)→ **#LR1/#LR3 的最佳落地**。
- 🟢 **B 数字检测式读数**:0-9 当 10 类检测 → 按 x 排序读数(车牌/水表技法)→ B 档候选,进 T125 bake-off。
- 🟡 **C 视觉签名事件检测**:"筹码出现"/"弃牌 overlay"/"亮边" 等类 → 位置无关事件信号。
- 🔴 **不接口**:多字符文字/中文 ID(YOLO 非序列识别器)→ 仍归 PaddleOCR。
- **真代价**:画框标注比分类重 + 多一个模型。
- **定位**:**前端升级,非起步件**。首个高帧原型仍固定 ROI + recognize-only 起步(零画框);YOLO 等固定 ROI 在高帧下脆弱真咬人 / 想灭 8v9 割裂时上。

## §8. 方案自检 — 盲区 + 漏洞复检(2026-06-01)

对"封存现架构 + 重建识别层(复用 CNN/ROI)+ 高帧+融合+求解器→95%"全案做 adversarial 自审。**主体成立,但 Tier 1 四洞不补 = 打看不见的靶 + 站未确认地基。**

### 🔴 Tier 1 — 地基级(不补 95% 无从谈起)
1. **没有 ground truth → 95% 当前不可度量** ⚠️ 最大洞。捕获率要"真实动作"对照,我们没有;pot-gap 是代理非真值;新旧 A/B 互比若都错只是错得不同。→ **必须人工标真值(看录像逐手,20-30 手)**,否则目标不可测。
2. **"信息在屏、只漏帧"核心论点没验地板**。预设动作/瞬间动画可能**一帧不渲染**(用户最早提过)。若"永不渲染"占比 >5% → **再高帧也封顶 <95%**。→ 从录像量这个地板。
3. **缺前置能力:原始高帧帧录制**。A/B + ground-truth 标注 + 可复现测试**全依赖存原始帧**;现在 live 处理不存帧。→ 先加录制能力。
4. **GPU 在用户机跑通没确认**。[[gpu-ocr-enable-sop]] 是"如何启用"SOP,暗示可能未验。高帧-on-GPU 压在未确认地基。→ T125 第 0 步先确认。

### 🟠 Tier 2 — 重塑 build
5. **捕获率 ≠ 可解手率(求解器被低估)**。PokerKit 要合法完整序列;单动作 95% 捕获,一手 20 动作平均漏 1 → 序列可能非法被拒 → 可解手率远低于 95%。**填缺口的反向搜索在未知缺口下可能组合爆炸**,工作量比 report 的乐观。
6. **追踪是错工具(自纠过度宣称)**。v1 固定 ROI → 元素不动,融合=「攒同 ROI 最近 N 帧 + 投票」,**不需 tracker**;ByteTrack 是给移动目标,只有 YOLO 检测前端才用。
7. **盲建 + 丢 Linux smoke**。DXcam Windows-only → 新捕获层 Linux 一行测不了,[[env-tooling-constraints]] 两段验证的 Linux smoke 这段没了,半盲迭代面放大。

### 🟡 Tier 3 — 过程/风险
8. **冻结旧管线会烂**:重建月级,期间 WePoker 改 UI → 旧 ROI 失效 + 新的没好 = 一个能用的都没有。
9. **融合投票需校准置信**:CNN softmax 常过度自信 → 系统性误读可能赢投票;融合非"取众数"。
10. **scope 蔓延(第二系统效应)**:greenfield 诱发镀金 DDD;守纪律到"新识别层 MVP"。

### 🔴 meta 洞:T125 spike 范围太窄
现只测**吞吐(几 Hz)**,但真问题是"**高帧后 pot-gap silent 25%→5% 了吗**" → 要跑完整新捕获测**捕获完整度**,非只测速度。**"能多快"≠"快了就抓得全"。**

### 修正后的真正第一步(比"建 spike"更靠前)
```
0. 确认用户机 GPU 跑通(#4)
1. 加原始高帧帧录制能力(#3)→ 录几段
2. 用户人工标 20-30 手真值(#1)+ 量"永不渲染"地板(#2)
3. 才是 T125 spike,范围扩到测「捕获完整度增益」非只测速度(meta)
4. 看数 → 建 → A/B(此时有真值可校准)
```
**最狠一句:不能命中一个无法度量的目标 → ground truth(#1)+ 帧录制(#3)必须在动手建之前钉进计划。**

## §10. 重大发现:WePoker 历史牌谱 = 识别层验收依据(2026-06-02)

**定位 = 识别层验收依据 / 校准源(非主路径)**:
- 比人工看回放标注**更准更省** → **录帧(record_frames)+ 手敲标注 降级/搁置**(§8 步骤序里的 ground-truth 改由 history 提供)

**验收循环**:打几手(pipeline live→DB)→ 读 DB 的 flop+识别结果 → 按 flop 在 history 翻到那手→截图 → 对比 history 真值 vs DB → **每手识别率**。

**衍生功能 → [[long-term-roadmap]] #LR19 牌谱校准**:监控到用户**主动调出** history → **被动 OCR** → 指纹 match DB 局 → 用权威牌谱**自动校准**历史数据。**红线干净**(被动 OCR 用户自调的画面,**无自动翻页=无输入注入**);自愈数据质量;同族 #LR12 主动学习。

## §12. T125 首测:OCR 吞吐 —— EasyOCR 到不了高帧 + recognize-only 证伪(2026-06-02)⭐

`tools/bench_ocr.py`,真实窗口帧(1454×1287)+ 74 个 OCR 文字区,3 路径每帧耗时:

| 路径 | ms/帧 | Hz | |
|---|---:|---:|---|
| A 逐 ROI readtext(现状) | 980 | **1.02** | 基准 |
| B readtext_batched | 1260 | 0.79 | **比 A 慢** |
| C recognize-only 整帧一次 | 1031 | 0.97 | **无提速** |

### 两个假设被数据打脸
- 🔴 **§7.1「recognize-only 免检测便宜化」证伪**:跳过检测(C)≈ 全量(A)→ **检测不是瓶颈,识别(CRNN)才是**;74 crop 的识别 ~1s,省检测省不掉。**"跳检测就快"错。**
- 🔴 **批处理(B)更慢**:`readtext_batched` 把所有 crop resize 到最大尺寸×3 → 小区被放大成大图 → 异构尺寸批处理=膨胀。

### 可信度
A 的 ~1Hz **吻合现 pipeline 已知 ~1Hz tick(OCR-bound)→ bench 可信**。

### 结论 + 方向
- **EasyOCR 无论哪条路 ≈ 1Hz,到不了 4-10Hz** → **高帧用 EasyOCR 走不通**。
- **真正提速杠杆没测**:§7.6 轻量识别器(PaddleOCR mobile / 自训小 CNN)—— 能把 74 crop **一次 batched forward** 跑完(单前向 vs 74 次重型 OCR),理论快一个量级。**命门现在窄成:小 CNN batched 跑 74 crop 多少 ms?**
- 附:74 = 全集,真 pipeline 跳弃牌座位 → 现实 ~2Hz(仍不够)。
- **价值**:便宜 bench 在建高帧管线前就拆穿"recognize-only 救场"错假设,免得白建。

### §7.1/§7.5/§5 更新
- §7.1「EasyOCR recognize-only 免训练起步」+ §7.5 同条 + §5 step1「recognize-only 起步」:**作为速度杠杆已证伪**(免检测不提速);仍可作免检测的便利,但**高帧提速必须靠轻量模型**。
- 下一 bench:`bench_cnn`(CardCNN batched 吞吐)= §7.6 速度假设的真检验。

## §13. 关键修正:分类 ≠ 序列识别(2026-06-02,bench_cnn + EasyOCR batch_size 重测 + context7)⭐

实测数据(74 文字区,真实窗口帧,GPU):
| | 速度 | 性质 |
|---|---|---|
| `bench_cnn` CardCNN | **2.7ms/74crop = 0.036ms/crop**(forward)、full 10.4ms→96Hz | **分类器**(定长 rank/suit,一次前向) |
| EasyOCR recognize bs=74 | **400ms/74 = 5.4ms/crop** → 2.5Hz | **序列识别**(CRNN+RNN+CTC) |
| PaddleOCR mobile rec(context7) | **4.8ms/crop 标准 / 1.23ms TensorRT** | 序列识别(轻量) |

### 我之前偷换概念(被用户直觉揪出)
- `bench_cnn` 测的是**分类器**(0.036ms/crop)→ **只代表 A 档类别字段(动作词)**,**不代表读数字**。
- **读多位数字 = 序列识别**(变长输出)→ ~5ms/crop,比分类重 **~150×**。我拿分类器速度暗示了整体识别速度 = apples-to-oranges。

### 三个实锤
1. **换轻量模型≈不提速(序列识别)**:PaddleOCR mobile 标准 4.8ms ≈ EasyOCR 5.4ms/crop → **~5ms/crop 对轻量 CRNN 基本与模型无关**。
2. **batch_size 批不掉**:EasyOCR bs 32→74 = 434→400ms 几乎不变 → ~5ms/crop 的 RNN+CTC 是地板,**不是 GPU 并行度问题**。
3. **EasyOCR + batch_size 也只到 2.5Hz**(1031→400ms)→ 改善但**仍不够 4-10Hz**。

### 让数字变快的三条路(都不是"换个 CNN")
| 路 | 速度 | 代价 |
|---|---|---|
| (a) **逐位分类**(固定槽/数字检测,0-9 当 10 类) | 分类器级 ~free | 切位/检测 + 字体固定假设(§7.6/§7.7) |
| (b) **序列识别 + TensorRT** | 4.8→1.23ms/crop(4×)→ 74crop ~91ms ~11Hz | TensorRT-RTX(§7.8) |
| (c) **规则反推,根本不读** | 0 | §3.1「解不读」—— 最便宜 |

### 修正后的高帧配方
- **A 档类别(动作词/牌型)** → CNN 分类器,~free(96Hz 实锤)✅
- **B 档数字** → **(c) 规则反推大多数(§3.1)** + 剩少数自由注额走 **(a) 逐位分类** 或 **(b) TensorRT**
- **绝不是"全换 CNN"** —— 那只解 A 档。

→ **§3.1「解不读」因此更核心**:序列识别是贵的那部分,**能不读就不读**是高帧关键;真要读的少数数字用逐位分类绕开 CRNN。
→ **T125 命门收敛**:高帧可行,配方 = 类别分类器(free)+ 数字「少读 + 逐位分类/TensorRT」;EasyOCR/PaddleOCR 整行序列识别(~5ms/crop)是死路,靠的不是换模型。

## §14. 柱子② 验证:规则反推「有条件成立」(2026-06-02,守恒-确定性分析)⭐

补上 §4 当年"求解器离线验不了"的洞 —— **现在有 history 真值(2 手),验了**。
**方法**:守恒+确定性分析(不用脆弱的 PokerKit 正向重放,精确起始筹码缺失会编造)。数**自由下注额**(玩家自选金额)vs **锚点**(底池+规则锁定+已抓)。关键:**跟注/盲注/ante 是规则锁定的(不自由),真自由的只有 下注/加注/all-in 的大小**。

### Ts2h5h —— ✅ 精确可解
自由额只有 1 个(那个 all-in;跟注=匹配它,限注=跟大盲,均锁定):
```
底池 470 = 非摊牌投入 36 + 2 摊牌者 ante 8 + 2A → A = (470−36−8)/2 = 213 ✓ 与真值分毫不差
```
→ **DB 漏掉、难 OCR 的大额 all-in 213,被底池+规则唯一解出。§3.1「解不读」在单次对抗结构上实锤。** 前提:抓到**结构**(谁弃/2人摊牌),金额不用读。

### 2hKs7s —— ⚠️ 底池单独欠定
自由额多个(preflop 加注28 + flop 下264 + all-in 144,跨街+边池)→ 1 个底池方程解不了多个自由额 → **欠定**,需多抓锚点(如已抓的 264 + all-in 那刻 stack→0)。边池/未跟回退不硬解(避免编造)。

### 判决(n=2)
**「规则反推漏掉的数字」真,但确定性有限,取决于「自由下注额数 vs 锚点数」**:
- 自由额少(单次对抗)→ 底池就够,精确解 ✓
- 多街多下注/边池 → 需多抓锚点,否则欠定
→ **同时印证 §8#5(捕获≠可解,会欠定)+ §3.1(解不读,确定时成立)**;§4 的洞答案 = **有条件成立**。

### 精确了"该抓什么"
捕获目标 = **结构(弃/all-in/跟 事件)+ 少数锚点(底池 + 偶尔下注额)**,**不是所有金额**。确定的手能解;欠定的手标低置信、不编造。
**caveat**:n=2;守恒-确定性法(非 PokerKit 重放);2hKs7s 边池未硬解。

## §15. 架构定稿:stack 主探测 + 多层交叉验证(2026-06-02,~15 轮 adversarial 收敛)⭐⭐

经十余轮对刺,从「捕获动作字幕 + 约束求解器」**收敛**到「stack 为主信号 + 多层交叉验证」。

### 核心洞察(用户)
**stack 是持久信号(永远在屏),动作字幕是瞬态信号(闪 0.x 秒)。** → 不追瞬态字幕,**密集读持久 stack,动作从 stack 变化反推**。绕开瞬态捕获的全部麻烦(永不渲染地板对动作消解)。

### 架构
```
高帧抓屏(DXcam/mss)
  → 每座 stack:多头定长数字 CNN(SVHN 式,一次前向,classifier 级)密集读 + 稳态融合
  → 局部恒等式(每玩家每动作):行前 stack = 下注额 + 行后 stack(三腿互验,缺一反解,违反则判误读)
  → 多街链式:Σ各街贡献 + 街间差额 再互验
  → 动作类型:跌幅 + 当前注 → 规则推(call/bet/raise/all_in;§3.1 解不读)
  → 弃/过:看下一轮"活跃玩家集"区分(状态机 + 双 OCR)
  → 公共牌 CNN → 分街(preflop/flop/turn/river);时间戳 → 定序
  → 手边界隔离手间补码;保险(走底池非持有,不动 stack)/盲/ante → 状态处理
OCR 退位:仅玩家 ID(开放文本,低频缓存)
全局底池守恒:外层兜底校验
```

### 为什么稳(对刺验证过的)
- **单点不可信、多维高可信**:局部恒等式 + 多街链 + 全局守恒 + 活跃集 = 多层交叉验证,自动抓误读/补缺。
- **数字读取已解**:多头定长 CNN(SVHN,街景 >96%;我们干净 UI 字体更易)= 识牌 CNN 同族 + 合成数据(§7.8)→ classifier 级速度、免切分/CRNN。
- 对刺结论:补码(手间,hand-seg 隔离)、保险(走底池不动持有 stack)、弃/过(活跃集分)、精度(局部恒等式救)—— 全被拆解。

### §15.1 仍不清晰的技术点(待 step 3 查 + step 4 验)
1. 🔴 **局部恒等式 reconcile 率**(整套产出率)—— 实测命门,需建。
2. **多头数字 CNN 在 WePoker 字体上的真准度 + 最大位数设定** —— SVHN 先例,未建未测。
3. **按街分段是否干净** —— 公共牌 CNN 检测街切换 + 动作能否准确归街(step 4 用真实数据验)。
4. 每座 stack ROI 高帧定位可靠性(+8v9 桌型)。
5. 弃/过时机判定依赖历史偏噪的弃牌检测。
6. 街内多次行动(下注→再加)的 stack 轨迹切分。
7. 自愿跌 vs 强制(盲/ante)的状态判别时机。
8. all-in 显% 的状态识别 + 金额取最后一读。

## §17. 持久信号修正 + 低成本"复活旧读法"试验(2026-06-02,用户实测纠前提)

> ⚠️ **推翻一条承重前提**:§15 此前说"动作字幕瞬态(闪 0.x 秒)、所以别读字幕改读 stack"。**用户实测:动作字幕不是瞬态。**

### §17.1 事实(用户实测)
- 每座**街内持久两路信号**(到本街结束才消失):**头像上方 = 动作词(类型)** + **下注区 = 对应金额(本街投入总额 = 最后一次的 raise-to/call-to)**。
- **同街多次行动 → 只显示最后一次**(动作词与金额都取最后态)。

### §17.2 对架构的影响(增强,非重做)
- **前提改写**:"字幕瞬态"❌ → "动作词 + 下注区金额**街内持久**"。data-reliability §0「信息在屏只停留 ~1s」/ gpu-ocr-sop「overlay 1-2s 抓不到」均据此修正。
- **每座三路持久信号**:动作词(类型)/ 下注区金额(本街投入,**比 stack-delta 更直接**;全座求和=本街池=又一守恒锚)/ stack(per-action 增量 + 跨街主干)。§15 之前把"读动作文字"降权(因假设瞬态),现**升回当直接互验**(词验类型、下注区验金额),不再只靠规则推+stack 反推。
- **高帧压力大松动**:难点从"抢拍 0.x 秒闪现" → "街内采样够密以抓状态变化";同座两次动作隔着别人行动(秒级)→ **中等帧率即可**,不必狂飙高帧。
- **很可能重新解释 25% 丢失**:老管线大概率追瞬态信号 / 只盯 timer 单座,而持久下注区整街、全座可读 → 信号一直可得,是抓法没对 → **95% 更可达**。

### §17.3 低成本试验提案(在大建前先验便宜路)
- **"旧架构"澄清**:指**现有运行管线**(读 action 文字 + 下注区),**不是**已封存的 phase-1-5 注意力/双OCR(那是单座 focus,与"读全座持久下注区"方向相反)。
- **大彩头**:自训多头数字 CNN + 高帧的唯一动因是"EasyOCR 读数字 ~1-2Hz 追不上瞬态"。若信号街内持久、中等帧率够 → **EasyOCR(慢但够准)可能直接够用 → 月级自训 CNN + 高帧那部分可能整个省掉**。
- **试验(离线、用已有 170343 帧、EasyOCR 测准度不测速)**:读每活跃座位的持久下注区金额 + 动作词贯穿一手,验 ① 街内稳定/街末清 ② 全座读得准否 ③ 能否重建各街投入(对账 stack-centric reconstruct + 看补回老管线漏的)。成本 ≈ 给 replay 工具加读 2 ROI/座,半天,零新数据。
- **caveat**:测"持久+可读性",非全管线;下注区仍 tier-B 数字(准度待验);Q2 街内多次动作只剩最后态 → 中间动作靠街内采样跳变 / stack-delta 补。
- **决策含义**:若试验 PASS → 捕获层可能走"中等帧 + EasyOCR 读持久下注区 + 约束求解器恢复",**大幅低于** stack-centric 自训 CNN 重建;两者也可融合(前端读三路持久信号,后端同一求解器)。**先验,再决定要不要大建。**

### §17.4 试验结果 + 决策:读取质量是瓶颈,回归原路(2026-06-02,用户拍板)
T129 在 170343 实跑 `--dump-actions` + `--fuse`,结论:
- **持久性 ✅ 确认**:下注区 amount 街内持久、清空点=街切换(验用户实测)。
- **下注区读得干净处=真数字**(132/128/210/58…对得上 stack 重建),但 **per-seat 覆盖不均**(seat0/6 弱);**动作词 OCR 太脏**(碎片/糊读,seat4=0)。
- **融合(无真值,相对数)**:并集 57 vs 单 stack 45 = **+12(+27%)**;但下注区单独(31)< stack,漏 stack 的 58% → **下注区是补充非替代**;两者都读到时一致率 79%。**估 ~70-80%,非 95%。**
- **🔑 判决:读取质量(per-seat ROI)是最大瓶颈,非信号可得性。** "下注区+EasyOCR+中等帧 → 省掉自训CNN+高帧大建" **证伪** —— 救不了场。
- **决策(用户)**:**调头回原路**(planned stack-centric 重建:读取质量靠 §3 三档识别器 / 自训数字 CNN / 高帧 + per-seat ROI 质量)。低成本实验已达目的,止于此。
- **不浪费的部分**:① 持久信号修正(§17.1)纳入认知;② **下注区留作融合/交叉验证第二信号**(实测补回 12 个 stack 漏的,`actions_from_bets`/`compare_coverage` 已入 reconstruct.py 备用);③ 多信号互补范式被实测支持。
- **真值仍是悬而未决的命门**:所有相对数证明"测不了绝对捕获率"——回原路后,ground truth(路A)+ T125 高帧/底池 benchmark 仍是必经。
